### Sustained-stream finding and `0.1.21` UDP prototype

The 200-frame physical gate above covers roughly four seconds and did not exercise steady-state socket behavior. A later 9,000-frame matrix reproduced the failure in both directions independently:

- The quiet-marker speaker-only run failed during its first control phase after roughly 30 seconds of actual streaming. Across that run and an immediately preceding manually interrupted speaker-only attempt, the device accumulated 521,280 downlink dropped bytes, 3,160 speaker-backpressure events, five partial writes, and two forced socket closes. Those totals establish sustained downlink failure, while they are cumulative rather than a clean per-run delta.
- The silent microphone-only run delivered 2,497 microphone frames, roughly 50 seconds of audio, before exhausting the host's two successful reconnects. It accumulated 637,824 uplink dropped bytes, three send failures, six send stalls, three forced closes, and a 4,808 ms maximum send duration. Downlink counters did not change.
- Natural full-duplex calls show the same socket flapping and eventually fail closed after the third transport loss in one logical session.

The matrix rules out acoustic echo and simultaneous microphone/speaker ownership as the complete explanation. The implemented **WSLANPCM** stack is not stable enough for a sustained Voice Session in either direction, and the bounded reconnect logic remains only a recovery guard. These runs do not isolate WebSocket framing from the surrounding send task, Wi-Fi, resampler, mixer, speaker-backpressure, or host-receive paths. **UDPPCM** is therefore a falsifiable replacement canary rather than an already-proven fix. A replacement media path needs to pass several minutes of speaker-only, microphone-only, and full-duplex traffic on the physical device before another end-to-end acceptance run.

Source candidate `0.1.21` separates two audible lifecycle cues. The existing `WakeBlip.flac` remains the immediate **wake heard** acknowledgement. The user-selected xylophone `sounds/ReadyBlip.flac` plays only when Joydex confirms the Realtime session, confirms an active device-media session, and publishes `Listening`. It is 1.397792 seconds of 48 kHz mono signed 16-bit FLAC, 33,613 bytes, with mean level -21.9 dBFS, peak -10.5 dBFS, and SHA-256 `DD8BBF928C4740378310C883323F9D1DC7DED0BA011875D027BA9364255B6377`. Starting either local cue flushes queued microphone audio, suppresses uplink for the cue, and retains an 80 ms post-cue tail so the acknowledgement is not fed back into Codex when barge-in is enabled.

The candidate retains the detecting wake profile: microphone gain `4`, Okay Computer cutoff `0.35`, five-frame window, VAD cutoff `0.10`, and pinned `esp-nn 1.1.2`. The prepared configuration confirms those exact fallback values; existing runtime tuning entities remain available.

`joydex-voice-pe-udp-prototype.yaml` adds one unencrypted IPv4 UDP endpoint on port `8766`. Microphone packets carry 20 ms / 640 bytes of 16 kHz PCM16; speaker packets carry 10 ms / 960 bytes of 48 kHz PCM16 and feed `joydex_voice_mixing_input` directly, removing the host 48→24 kHz and device 24→48 kHz conversion pair. Each direction has an independent zero-based sequence and a 400 ms oldest-drop PSRAM queue. The endpoint rejects oversized datagrams without accepting a truncated frame. The host pings once per second, the device expires an unresponsive peer after 3.5 seconds, and close emits a short acknowledgement burst. `Joydex Audio Barge In` remains persisted and remotely configurable; it must be on for the duplex physical gate. This sustained-stream prototype omits speaker flush because interruption requires an acknowledged control/data ordering boundary; that remains an explicit Joydex-integration gate.

The pure packet codec, standalone host client, and loopback peer live in `tools\Joydex.VoicePeUdpPrototype`; `scripts\run-udp-pcm-prototype.ps1` builds and runs all three host-loopback directions in one command. The reviewed 30-second matrix passed 3,000/3,000 speaker frames, 1,500/1,500 microphone frames, and the combined 3,000 + 1,500 duplex case, with zero missing, late, or invalid packets and a clean closed session in every case. Speaker-only carried zero microphone frames during playback; duplex carried all 1,500. Speaker-only pacing had 2.804 ms maximum lateness, a 12.804 ms maximum interval, and no catch-up intervals; duplex had 1.602 ms, 11.602 ms, and no catch-up intervals. The pacing gate also rejects more than one percent catch-up intervals. This validates the host protocol only; it does not exercise Voice PE Wi-Fi, FreeRTOS scheduling, the physical microphone, or speaker output.

Device mode wraps UDP with exact identity/version checks, Starting/Listening/Armed lifecycle control, barge-in control, wake/microphone checks, counter deltas, close verification, and rearm. A host start gate makes its three-second settle begin only after `Listening`, leaving room for the xylophone cue before test PCM. Per-session gauges fail above 6,400 uplink-queue bytes, 19,200 downlink-queue bytes, a 100 ms main-loop gap, or a 20 ms uplink send. Runs shorter than 180 seconds are labeled smoke tests and cannot satisfy the adoption-matrix field; speaker-only, microphone-only, and duplex must each run for at least three minutes on the physical device. The running Joydex process still used WSLANPCM during this experiment; UDP was deliberately not integrated and was later superseded by the Sendspin Opus downlink below.

Only after a corrected UDP candidate passes a short physical smoke should the full qualification run as three commands:

```powershell
.\scripts\run-udp-pcm-prototype.ps1 -DeviceHost 192.0.2.10 -Direction speaker-only -Seconds 180
.\scripts\run-udp-pcm-prototype.ps1 -DeviceHost 192.0.2.10 -Direction microphone-only -Seconds 180
.\scripts\run-udp-pcm-prototype.ps1 -DeviceHost 192.0.2.10 -Direction duplex -Seconds 180
```
